# สเปก: ซอฟต์แวร์ปิดลูป B2B ส่งออก + บันทึกศึกษา Fall Detection (ฉบับร่าง)

## ส่วน A — Closed-loop ขายส่งออก B2B

**เสิร์ฟกลุ่ม:** 1 ผู้ผลิต (OTOP/วิสาหกิจ) และ 2 คนกลาง (ผู้ส่งออก/ชิปปิ้ง/โลจิสติกส์) | Agent: `producer-agent`, `intermediary-agent`

**ข้อจำกัดจากโปรเจกต์ (ห้ามละเมิด):** ชำระเงิน THB ผ่าน Omise เท่านั้น, Supabase Postgres, ไม่มี Stripe/USD escrow/Neo4j (ปฏิเสธใน `DECISIONS_LOG.md` 2026-07-01), Affiliate จ่ายจากยอดขายจริง ลึกไม่เกิน 2 ชั้น, PDPA ก่อนเสมอ

### ลูปการทำงาน (6 ขั้น)
| # | ขั้น | สิ่งที่ระบบทำ | ผลลัพธ์ที่ตรวจสอบได้ |
|---|---|---|---|
| 1 | Lead intake | รับ RFQ จากผู้ซื้อ จัดหมวด HS code เบื้องต้น | แถว `rfq` + สถานะ |
| 2 | Match | จับคู่ผู้ผลิต (pgvector ค้นสินค้าที่คล้าย) | รายชื่อผู้ผลิตพร้อมเหตุผลการจับคู่ |
| 3 | Quote | ร่างใบเสนอราคา (THB) + เงื่อนไข Incoterms | PDF/เอกสารร่าง ให้คนอนุมัติ |
| 4 | Export docs | เช็กลิสต์เอกสาร (Invoice, Packing List, C/O ฯลฯ) | checklist ครบ/ขาด |
| 5 | Fulfil | สถานะจัดส่งที่ผู้ใช้กรอกเอง (ไม่ติดตามเรือ/real-time) | timeline |
| 6 | Feedback | ปิดเคส เก็บปัญหา → กลับไปปรับขั้น 2–4 | บันทึกบทเรียนต่อเคส |

**Human-in-the-loop:** ขั้น 3 และ 4 ต้องมีคนอนุมัติก่อนส่งออกนอกระบบ (ห้ามส่งอัตโนมัติ)

### สิ่งที่ยังไม่ได้ทำ / ต้องตัดสินใจ
- ยังไม่มี migration/route/UI; ยังไม่ได้ตรวจกฎศุลกากรจริง (ต้องให้ผู้เชี่ยวชาญยืนยัน)
- ยังไม่ได้วัด conversion หรือเวลาประหยัดได้ — ห้ามอ้างตัวเลขจนกว่าจะทดลองจริง

## ส่วน B — บันทึกศึกษา Fall Detection และนิยาม "สถานการณ์ซับซ้อน"

**เสิร์ฟกลุ่ม:** 6 สายงานวิชาชีพ (พยาบาล/ผู้ดูแล) และ 4 ผู้บริโภค (ครอบครัวผู้สูงอายุ) | Agent: `professional-agent`, `consumer-agent`

**ขอบเขตด้านจริยธรรม:** ใช้ pose/skeleton หรือเซนเซอร์เท่านั้น **ไม่ระบุตัวตนจากใบหน้า** และต้องมีความยินยอมตาม PDPA (ข้อมูลสุขภาพเป็นข้อมูลอ่อนไหว) ประมวลผลในประเทศ/on-premise

### นิยามสถานการณ์ซับซ้อน (ร่าง)
การบดบังบางส่วน (occlusion), แสงน้อย/ย้อนแสง, หลายคนในเฟรม, ล้มจากเตียง/เก้าอี้, นั่งลงเร็ว vs ล้มจริง (false positive), มุมกล้องเปลี่ยน

### ท่อประมวลผลที่แนะนำ
กล้อง → ตรวจจับคน (object detection) → ติดตามต่อเนื่อง (tracking) → ประมาณท่าทาง (pose) → ตัวจำแนกเหตุการณ์ล้ม → แจ้งเตือนผู้ดูแล

### ตัวชี้วัดที่ต้องวัดเองก่อนอ้างผล
Recall/Precision ของการล้ม, อัตรา false alarm ต่อวัน, latency — **ยังไม่ได้วัด**; ต้องระบุชุดข้อมูล วันที่ และวิธีวัดทุกครั้ง

### งานอ่านเปเปอร์
ยังไม่ได้ค้น/ตรวจเปเปอร์จริงในเซสชันนี้ — ห้ามอ้างชื่อเปเปอร์/ผลลัพธ์จากความจำ ขั้นต่อไป: ค้นด้วยเครื่องมือค้นหา แล้วบันทึกเฉพาะที่ตรวจสอบได้ พร้อม DOI

## ส่วน C — เนื้อหาสมมติ (ติดป้ายชัดเจน)
