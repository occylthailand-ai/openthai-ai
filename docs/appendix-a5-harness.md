## 🎯 เหตุผลที่ต้องมีภาคผนวกนี้

คนส่วนใหญ่ที่เริ่มใช้ AI คิดว่าปัญหาทุกอย่างแก้ได้ด้วย **"เขียนคำสั่งให้ดีขึ้น"**

นั่นคือความเข้าใจผิดที่แพงที่สุดในวงการ

เวลาระบบ AI ตอบผิด มันมีอย่างน้อย **สามสาเหตุที่แตกต่างกันโดยสิ้นเชิง** และแต่ละสาเหตุแก้คนละที่:

- ถ้าโมเดล **ไม่ทำตามที่สั่ง** → ปัญหาอยู่ที่ **Prompt**
- ถ้าโมเดล **ไม่รู้ข้อมูลที่ควรรู้ หรือลืมสิ่งที่เพิ่งคุย** → ปัญหาอยู่ที่ **Context**
- ถ้าโมเดล **ทำงานหลายขั้นแล้วหลุดกลางทาง ไม่ตรวจตัวเอง** → ปัญหาอยู่ที่ **Harness**

การเอา Prompt ไปแก้ปัญหา Context เหมือนการขันน็อตด้วยไขควงผิดหัว — ยิ่งขันยิ่งเสีย

ภาคผนวกนี้แยกสามระดับนี้ให้ชัด พร้อมตารางวินิจฉัย ลูปมาตรฐาน และตัวอย่างที่ใช้ได้จริงกับ 6 กลุ่มผู้ใช้ของ OpenThaiAi

## A5.1 สามระดับของการออกแบบระบบ AI

### ภาพรวม — หน่วยของงานต่างกันอย่างไร

```
┌───────────────────────────────────────────────────────────────┐
│  ระดับ 3: HARNESS ENGINEERING                                 │
│  หน่วยของงาน = "ทั้งภารกิจ" จนจบ                              │
│                                                               │
│   ┌─────────────────────────────────────────────────────┐     │
│   │  ระดับ 2: CONTEXT ENGINEERING                       │     │
│   │  หน่วยของงาน = "สิ่งที่อยู่ในหน้าต่างบริบทแต่ละก้าว"  │     │
│   │                                                     │     │
│   │    ┌───────────────────────────────────────────┐    │     │
│   │    │  ระดับ 1: PROMPT ENGINEERING              │    │     │
│   │    │  หน่วยของงาน = "1 input"                  │    │     │
│   │    │                                           │    │     │
│   │    │   Role → Context → Instructions           │    │     │
│   │    │   → Examples → Format                     │    │     │
│   │    └───────────────────────────────────────────┘    │     │
│   │                                                     │     │
│   │    เลือก / บีบอัด / ตัดทิ้ง ให้พอดีงบโทเคน           │     │
│   └─────────────────────────────────────────────────────┘     │
│                                                               │
│    Gather → Act → Verify → (ไม่ผ่าน) → retry → จนผ่านเกณฑ์     │
└───────────────────────────────────────────────────────────────┘
```

**กฎอ่านภาพ:** ระดับนอกครอบระดับใน — Harness เรียก Context หลายรอบ, Context หนึ่งรอบบรรจุ Prompt หนึ่งชุด
คุณ **ข้ามระดับไม่ได้** แต่คุณ **เลือกได้ว่าจะหยุดที่ระดับไหน** ตามความยากของงาน

### A5.1.1 ระดับ 1 — Prompt Engineering (หน่วยของงาน = 1 input)

**นิยาม:** ศิลปะการเรียบเรียง *ข้อความหนึ่งชุด* ให้โมเดลเข้าใจว่าต้องทำอะไร ในรูปแบบไหน

**องค์ประกอบ 5 ส่วนมาตรฐาน:**

| # | ส่วนประกอบ | หน้าที่ | ตัวอย่างภาษาไทย |
|---|---|---|---|
| 1 | **Role** (บทบาท) | บอกว่าโมเดลสวมหมวกใบไหน | "คุณคือนักบัญชีภาษีอากรที่ปรึกษา SME ไทย" |
| 2 | **Context** (บริบท) | ข้อมูลแวดล้อมที่จำเป็นต่อคำตอบ | "ลูกค้าเป็นวิสาหกิจชุมชน จดทะเบียนปี 2567 รายได้ต่ำกว่า 1.8 ล้าน" |
| 3 | **Instructions** (คำสั่ง) | สิ่งที่ต้องทำ ทีละข้อ ชัดเจน | "1) ระบุว่าต้องจด VAT หรือไม่ 2) อ้างมาตราที่เกี่ยวข้อง" |
| 4 | **Examples** (ตัวอย่าง) | แสดงผลลัพธ์ที่ต้องการ (few-shot) | ตัวอย่างคำตอบที่ถูก 1–3 ชุด |
| 5 | **Format** (รูปแบบ) | โครงสร้างคำตอบที่บังคับ | "ตอบเป็น JSON: `{สรุป, มาตรา[], ข้อควรระวัง}`" |

**ปัญหาที่ Prompt แก้ได้:**
- คำตอบผิดรูปแบบ (อยากได้ JSON ได้ร้อยแก้ว)
- น้ำเยอะ / สั้นเกินไป / โทนไม่เหมาะ
- ไม่ทำตามลำดับขั้นที่สั่ง
- ภาษาปนอังกฤษทั้งที่อยากได้ไทยล้วน

**ปัญหาที่ Prompt แก้ไม่ได้ (สำคัญมาก):**
- ❌ โมเดลไม่รู้ข้อมูลที่ไม่เคยเห็น — ไม่ว่าจะเขียน prompt สวยแค่ไหน
- ❌ โมเดลลืมสิ่งที่คุยไป 40 เทิร์นก่อน
- ❌ งานที่ต้องเรียกเครื่องมือภายนอกหลายรอบ

> **หลักการเหล็ก:** ถ้าคุณกำลังเขียน prompt ว่า *"อย่าแต่งข้อมูล ให้ตอบตามความจริงเท่านั้น"*
> แปลว่าคุณกำลังใช้เครื่องมือผิดระดับ — ปัญหานี้แก้ที่ retrieval ไม่ใช่ที่ prompt

### A5.1.2 ระดับ 2 — Context Engineering (หน่วยของงาน = สิ่งที่อยู่ในหน้าต่างบริบทแต่ละก้าว)

**นิยาม:** ศิลปะการจัดการ *ความจำ* ของระบบ — ตัดสินใจว่า ณ ก้าวนี้ อะไรควรอยู่ในหน้าต่างบริบท และอะไรควรถูกทิ้ง

หน้าต่างบริบท (context window) คือ **งบประมาณจำกัด** เหมือนกระเป๋าเป้ที่มีน้ำหนักบรรทุกสูงสุด
งานของ Context Engineer คือทำหน้าที่ **ภัณฑารักษ์ (Curator)** — ไม่ใช่คนขนของ

```
       แหล่งข้อมูลขาเข้า (Candidates)
   ┌──────────────────────────────────────┐
   │  • User query        (คำถามผู้ใช้)     │
   │  • System prompt     (กฎประจำระบบ)    │
   │  • Retrieved docs    (เอกสารที่ค้นมา)  │
   │  • Tool outputs      (ผลจากเครื่องมือ) │
   │  • Memory            (ความจำระยะยาว)   │
   │  • Prior turns       (บทสนทนาก่อนหน้า) │
   └──────────────┬───────────────────────┘
                  │
                  ▼
        ╔═══════════════════════╗
        ║      CURATOR          ║   ← หัวใจของ Context Engineering
        ║  ┌─────────────────┐  ║
        ║  │ SELECT  เลือก    │  ║   จัดอันดับความเกี่ยวข้อง (re-rank)
        ║  │ COMPRESS บีบอัด  │  ║   สรุป / ตัดหัวท้าย / dedupe
        ║  │ DROP    ตัดทิ้ง  │  ║   ทิ้งของเก่าที่ไม่ถูกอ้างถึงแล้ว
        ║  └─────────────────┘  ║
        ╚═══════════┬═══════════╝
                    │
                    ▼
   ┌──────────────────────────────────────┐
   │   CONTEXT WINDOW (งบจำกัด)            │
   │   ████████████████░░░░░░  ใช้ไป 70%   │
   │   ต้องเหลือที่ให้ "คำตอบ" ด้วยเสมอ     │
   └──────────────────────────────────────┘
```

**เทคนิคหลักของ Context Engineering:**

| เทคนิค | ทำอะไร | ใช้เมื่อ |
|---|---|---|
| **Retrieval (RAG)** | ค้นเอกสารจริงมาใส่ก่อนตอบ | ต้องการความถูกต้องเชิงข้อเท็จจริง + อ้างอิงได้ |
| **Re-ranking** | เรียงเอกสารที่ค้นได้ใหม่ตามความเกี่ยวข้องจริง | ค้นได้ 50 ชิ้น แต่ใส่ได้ 5 ชิ้น |
| **Summarization / Compaction** | ยุบบทสนทนาเก่าเป็นสรุปสั้น | สนทนายาว เริ่มชนเพดานโทเคน |
| **Memory (ระยะยาว)** | เก็บข้อเท็จจริงถาวรนอกหน้าต่าง แล้วดึงมาเฉพาะที่ใช้ | ผู้ใช้คนเดิมกลับมาใหม่ในอีกสัปดาห์ |
| **Chunking ภาษาไทย** | ตัดเอกสารเป็นก้อนโดยเคารพขอบเขตประโยคไทย | ไทยไม่มีเว้นวรรค ตัดผิด = ความหมายเพี้ยน |
| **Structured note-taking** | ให้เอเจนต์จดสรุปลงไฟล์นอก context แล้วอ่านกลับ | ภารกิจยาวเกินหนึ่งหน้าต่าง |

**ปัญหาที่ Context แก้ได้:**
- ตอบผิดข้อเท็จจริง / แต่งเรื่อง (hallucination) — เพราะไม่มีเอกสารจริงให้ยึด
- ลืมสิ่งที่คุยไปแล้ว
- ตอบด้วยข้อมูลเก่าล้าสมัย
- ดึงเอกสารมาผิดเรื่อง

**ปัญหาที่ Context แก้ไม่ได้:**
- ❌ งานที่ต้องลงมือทำหลายขั้นและตรวจผลตัวเอง (เช่น เขียนโค้ด → รันเทสต์ → แก้ → รันใหม่)
- ❌ ยัดข้อมูลเข้าไปเยอะ ๆ แล้วหวังว่าโมเดลจะฉลาดขึ้น — ตรงกันข้าม คุณภาพมักตกลง (ดู A5.6)

### A5.1.3 ระดับ 3 — Harness Engineering (หน่วยของงาน = ทั้งภารกิจจนจบ)

**นิยาม:** การออกแบบ *ทั้งเครื่องจักร* ที่ห่อโมเดลไว้ — เครื่องมือที่เรียกได้, เอเจนต์ย่อยที่แตกงานได้, ตัวตรวจสอบที่บอกว่าผ่านหรือไม่ผ่าน, และเงื่อนไขว่าจะวนซ้ำหรือหยุด

คำว่า *harness* แปลตรงตัวว่า "สายรัดเทียม" — สิ่งที่เอาไว้บังคับม้าให้ลากเกวียนไปในทิศที่ต้องการ
โมเดลคือม้า **Harness คือทุกอย่างที่เหลือ**

```
                    ┌─────────── HARNESS ───────────┐
                    │                               │
   ภารกิจเข้า ────► │  ╔═════════╗                  │
                    │  ║ GATHER  ║  รวบรวมสิ่งที่ต้องรู้
                    │  ╚════╤════╝  (ค้นไฟล์ / เรียก API / อ่าน DB)
                    │       ▼                       │
                    │  ╔═════════╗                  │
                    │  ║   ACT   ║  ลงมือทำหนึ่งก้าว │
                    │  ╚════╤════╝  (เขียน / แก้ / เรียก tool)
                    │       ▼                       │
                    │  ╔═════════╗                  │
                    │  ║ VERIFY  ║  ตรวจว่าผ่านเกณฑ์ไหม
                    │  ╚════╤════╝  (test / schema / rule / LLM-judge)
                    │       │                       │
                    │   ผ่าน?├── ไม่ ──┐             │
                    │       │         │ retry       │
                    │       │         └──► กลับไป GATHER
                    │      ใช่                       │
                    │       ▼                       │
                    │   ส่งมอบผลลัพธ์ + หลักฐานการตรวจ │
                    └───────────────────────────────┘

   องค์ประกอบที่ต้องออกแบบ:
   • TOOLS      — โมเดลเรียกอะไรได้บ้าง (อ่านไฟล์ ค้นเว็บ รันโค้ด query DB)
   • SUB-AGENT  — งานย่อยไหนควรแตกให้เอเจนต์เฉพาะทางทำ แล้วส่งกลับแค่สรุป
   • VERIFIER   — เกณฑ์ผ่าน/ไม่ผ่านที่ "เครื่องตัดสินได้" ไม่ใช่ความรู้สึก
   • BUDGET     — จำกัดจำนวนรอบ / โทเคน / เวลา ไม่งั้นลูปไม่จบ
   • GUARDRAILS — ชั้นกรอง input (prompt injection) และ output (PII, hate speech)
```

**ปัญหาที่ Harness แก้ได้:**
- งานหลายขั้นที่ทำไม่จบในเทิร์นเดียว
- ระบบไม่ตรวจงานตัวเอง ส่งของเสียออกมา
- ต้องเรียกข้อมูลจริงจากระบบภายนอก (ERP, คลังสินค้า, ราคาตลาด)
- ต้องการหลักฐานว่า "ทำไมถึงตอบแบบนี้" (audit trail)

**ต้นทุนที่ต้องยอมรับ:** Harness แพงกว่า Prompt หลายเท่าทั้งด้านโทเคนและเวลา
อย่าสร้าง harness ให้กับงานที่ prompt เดียวก็จบ

### A5.1.4 ตารางเทียบสามระดับ

| มิติ | Prompt Engineering | Context Engineering | Harness Engineering |
|---|---|---|---|
| **หน่วยของงาน** | 1 input | สิ่งที่อยู่ใน context window แต่ละก้าว | ทั้งภารกิจจนจบ |
| **คำถามหลัก** | "จะสั่งอย่างไรให้ทำถูก" | "ณ ก้าวนี้ โมเดลควรเห็นอะไรบ้าง" | "ระบบจะรู้ได้อย่างไรว่างานเสร็จแล้วจริง" |
| **สิ่งที่ควบคุม** | ถ้อยคำ โครงสร้างคำสั่ง ตัวอย่าง | การเลือก/บีบอัด/ตัดทิ้งข้อมูล | tools, sub-agents, verifier, เงื่อนไขหยุด |
| **แก้ปัญหา** | ผิดรูปแบบ / ไม่ทำตามสั่ง | ลืม / ไม่รู้ / ดึงผิด / context ล้น | ทำไม่จบ / ไม่ตรวจตัวเอง / ต้องใช้ระบบภายนอก |
| **ต้นทุนพัฒนา** | ต่ำ (นาที–ชั่วโมง) | กลาง (วัน–สัปดาห์) | สูง (สัปดาห์–เดือน) |
| **ต้นทุนรัน** | 1 เรียก | 1–3 เรียก + ค่า retrieval | N เรียก (N = จำนวนรอบ) |
| **วัดผลด้วย** | pass rate ของ format/instruction | recall@k, precision, groundedness | task completion rate, จำนวนรอบเฉลี่ย, ต้นทุนต่อภารกิจ |
| **ล้มเหลวแบบไหน** | ตอบไม่ตรงรูปแบบ | ตอบมั่นใจแต่ผิด | วนไม่จบ / เผาโทเคน / ทำเกินขอบเขต |

## A5.2 ตารางวินิจฉัย — "อาการแบบนี้ ต้องแก้ที่ระดับไหน"

ใช้ตารางนี้ก่อนลงมือแก้ทุกครั้ง อ่านจากซ้ายไปขวา

| # | อาการที่เห็น | สาเหตุที่แท้จริง | แก้ที่ระดับ | วิธีแก้ที่ควรทำ | ❌ วิธีที่คนมักทำผิด |
|---|---|---|---|---|---|
| 1 | ตอบผิดข้อเท็จจริง / แต่งตัวเลขขึ้นมาเอง | ไม่มีเอกสารจริงในบริบท | **Context** | เพิ่ม RAG + บังคับ citation + ถ้าไม่พบให้ตอบ "ไม่พบข้อมูล" | เติม prompt ว่า "ห้ามแต่งข้อมูล" |
| 2 | ตอบถูกเนื้อหา แต่รูปแบบเพี้ยน (อยากได้ JSON) | คำสั่งรูปแบบไม่ชัด | **Prompt** | ระบุ schema + ให้ตัวอย่าง + ใช้ structured output | ไปเพิ่มเอกสารใน RAG |
| 3 | ลืมสิ่งที่ผู้ใช้บอกไป 30 เทิร์นก่อน | บทสนทนาเก่าถูกตัดทิ้ง | **Context** | สรุปบทสนทนาเป็นก้อน + memory ระยะยาว | เพิ่มขนาดโมเดล |
| 4 | ทำงานหลายขั้นแล้วหยุดกลางทาง ไม่ทำต่อ | ไม่มีลูป ไม่มีเงื่อนไข "ยังไม่เสร็จ" | **Harness** | ใส่ Gather→Act→Verify + retry จนผ่านเกณฑ์ | เขียน prompt ว่า "ทำให้ครบทุกขั้น" |
| 4b | ส่งงานออกมาทั้งที่ยังผิด ไม่เคยตรวจเอง | ไม่มี verifier | **Harness** | เพิ่มตัวตรวจที่ตัดสินได้ด้วยเครื่อง (test, schema, rule) | ขอให้โมเดล "ตรวจให้ดี ๆ" |
| 5 | ค้นเอกสารมาได้ แต่มาผิดเรื่อง | embedding/chunking ภาษาไทยแย่ | **Context** | ปรับ chunking ตามขอบเขตประโยคไทย + re-ranking | เขียน prompt ให้ยาวขึ้น |
| 6 | ใส่ข้อมูลเยอะขึ้นแล้วคำตอบแย่ลง | context ล้น / ข้อมูลรบกวน | **Context** | ตัดทิ้ง + re-rank เอาเฉพาะ top-k ที่เกี่ยวจริง | ใส่เพิ่มอีก |
| 7 | โทนภาษาไม่เหมาะ (ทางการเกิน/กันเองเกิน) | ไม่ได้ระบุ role และผู้ฟัง | **Prompt** | กำหนด Role + กลุ่มผู้ฟัง + ตัวอย่างโทน | fine-tune โมเดลใหม่ |
| 8 | ตอบด้วยข้อมูลปีเก่า | ไม่มีการดึงข้อมูลสด | **Context** | ต่อ retrieval เข้ากับแหล่งข้อมูลที่อัปเดต + ใส่วันที่ในบริบท | เตือนใน prompt ว่า "ตอนนี้ปี 2569" |
| 9 | ต้องใช้ตัวเลขจริงจากระบบหลังบ้าน (สต็อก/ราคา) | โมเดลเข้าถึงระบบไม่ได้ | **Harness** | สร้าง tool ให้เรียก API จริง | ให้ผู้ใช้ copy-paste ข้อมูลมาเอง |
| 10 | ลูปวนไม่จบ เผาโทเคน | ไม่มีเงื่อนไขหยุด / เกณฑ์ผ่านคลุมเครือ | **Harness** | กำหนด max rounds + เกณฑ์ผ่านที่วัดได้ + fallback ส่งต่อมนุษย์ | เพิ่ม budget โทเคน |
| 11 | ผู้ใช้แอบสั่งให้ระบบเปิดเผยคำสั่งลับ | ไม่มี input guardrail | **Harness** | เพิ่มชั้นกรอง prompt injection ก่อนเข้าโมเดล | เขียนใน system prompt ว่า "ห้ามบอก" |
| 12 | คำตอบหลุด PII / คำหยาบ | ไม่มี output guardrail | **Harness** | เพิ่มชั้นตรวจ output ก่อนส่งถึงผู้ใช้ | หวังว่าโมเดลจะไม่ทำ |
| 13 | ตอบดีเวลาทดสอบ แต่แย่กับผู้ใช้จริง | ไม่มีชุดวัดผลที่สะท้อนงานจริง | **ทุกระดับ** | สร้าง Thai Eval Suite จากเคสจริง + วัดก่อน/หลังทุกครั้ง | เชื่อความรู้สึกว่า "ดีขึ้นแล้ว" |

> **วิธีใช้ตารางนี้เร็ว ๆ:**
> ถามตัวเอง 3 คำถามตามลำดับ
> 1. โมเดล **"รู้"** สิ่งที่ควรรู้หรือยัง → ถ้าไม่ = Context
> 2. โมเดล **"เข้าใจ"** ว่าต้องทำอะไรหรือยัง → ถ้าไม่ = Prompt
> 3. ระบบ **"รู้ได้เอง"** ไหมว่างานเสร็จหรือยัง → ถ้าไม่ = Harness

## A5.3 Loop 5 ขั้นมาตรฐาน

OpenThaiAi ใช้ลูปมาตรฐาน 5 ขั้นเดียวกันทั้งองค์กร (สอดคล้องกับ `CLAUDE.md` ข้อ 4)

```
   ┌──────────────┐
   │ 1. DISCOVER  │  รู้ก่อนทำ — อ่านของเดิม ค้นข้อมูล ถามให้ชัด
   │  (UNDERSTAND)│  ผลลัพธ์: รายการข้อเท็จจริง + สิ่งที่ยังไม่รู้
   └──────┬───────┘
          ▼
   ┌──────────────┐
   │ 2. PLAN      │  แตกงานเป็นก้อนเล็ก ระบุ edge case + เกณฑ์ผ่าน
   │              │  ผลลัพธ์: checklist ที่ตรวจได้ทีละข้อ
   └──────┬───────┘
          ▼
   ┌──────────────┐
   │ 3. EXECUTE   │  ทำทีละก้อน ไม่ทำรวดเดียวจบ
   │              │  ผลลัพธ์: ของจริง (ไฟล์/โค้ด/คำตอบ)
   └──────┬───────┘
          ▼
   ┌──────────────┐
   │ 4. VERIFY    │  ตรวจด้วยเกณฑ์ที่ตั้งไว้ในขั้น PLAN
   │              │  ผลลัพธ์: ผ่าน / ไม่ผ่าน + เหตุผลที่ชี้จุดได้
   └──────┬───────┘
          │
     ผ่าน?├──── ไม่ ────┐
          │             ▼
         ใช่     ┌──────────────┐
          │      │ 5. ITERATE   │  แก้เฉพาะจุดที่ fail
          │      │              │  แล้วกลับไปขั้นที่เหมาะสม
          │      └──────┬───────┘
          │             │
          │             └──► กลับไป 1 (ถ้าข้อมูลผิด)
          │                        หรือ 3 (ถ้าแค่ทำผิด)
          ▼
      ✅ ส่งมอบ + ระบุสิ่งที่ยังไม่ได้ทำ
```

**กฎเหล็กของลูป:**
1. ขั้น PLAN **ต้องเขียนเกณฑ์ผ่านก่อน** ลงมือ — ถ้าเขียนไม่ได้ แปลว่ายังไม่เข้าใจงาน
2. ขั้น VERIFY ต้องตอบได้ว่า *"ผ่าน/ไม่ผ่าน"* ไม่ใช่ *"ดูดีนะ"*
3. ITERATE ต้องมี **เพดานรอบ** เสมอ (แนะนำ 3–5 รอบ) เกินแล้วส่งต่อมนุษย์
4. ทุกรอบต้อง **แคบลง** — ถ้ารอบที่ 3 ยังแก้ปัญหาเดิม แปลว่าวินิจฉัยผิดระดับ กลับไปดู A5.2

### A5.3.1 ลูปจริงแบบที่ 1 — Coding Loop

ใช้เมื่อ: เขียน/แก้โค้ด, สร้าง API, migrate ฐานข้อมูล

```
DISCOVER  │ อ่านโค้ดเดิม + โครงสร้างโปรเจกต์ + เทสต์ที่มีอยู่
          │ tool: read_file, grep, list_dir
          ▼
PLAN      │ แตกเป็น: (1) แก้ schema (2) แก้ service (3) เพิ่มเทสต์
          │ เกณฑ์ผ่าน: เทสต์ทั้งชุดเขียว + lint ผ่าน + ไม่มี type error
          ▼
EXECUTE   │ แก้ทีละไฟล์ commit ย่อย
          ▼
VERIFY    │ รัน `pytest` + `ruff` + `mypy`  ← เครื่องตัดสิน ไม่ใช่โมเดลตัดสิน
          ▼
ITERATE   │ อ่าน stack trace → แก้เฉพาะไฟล์ที่ fail → รันใหม่ (สูงสุด 5 รอบ)
```

**Verifier ที่ใช้:** ตัวรันเทสต์ (deterministic) — นี่คือลูปที่ verify ได้แม่นที่สุด เพราะเครื่องตัดสินได้เอง

---

### A5.3.2 ลูปจริงแบบที่ 2 — Research Loop

ใช้เมื่อ: ค้นข้อมูลกฎหมาย, สำรวจราคาตลาด, ตรวจสอบข้อเท็จจริง

```
DISCOVER  │ แตกคำถามใหญ่เป็นคำถามย่อย 3–7 ข้อ
          │ ค้นแบบกระจาย (fan-out) หลายคำค้น หลายแหล่ง
          ▼
PLAN      │ กำหนด: ต้องได้แหล่งอ้างอิงกี่แหล่งต่อข้อสรุป (แนะนำ ≥2 แหล่งอิสระ)
          │ เกณฑ์ผ่าน: ทุกข้อความเชิงข้อเท็จจริงมี citation + ไม่มีแหล่งขัดแย้งที่ยังไม่อธิบาย
          ▼
EXECUTE   │ อ่านแหล่งจริง (ไม่ใช่ snippet) → สกัดข้อเท็จจริง → บันทึกพร้อม URL + วันที่
          ▼
VERIFY    │ ตรวจย้อน: ทุกประโยคที่มีตัวเลข/ชื่อ/วันที่ ชี้กลับไปแหล่งได้ไหม
          │ ตรวจความขัดแย้ง: มีแหล่งไหนบอกตรงข้ามไหม
          ▼
ITERATE   │ ข้อไหนยังไม่มีแหล่งยืนยัน → ค้นเพิ่มเฉพาะข้อนั้น
          │ ถ้าค้นแล้วยังไม่พบ → เขียนว่า "ไม่พบข้อมูลยืนยัน" ห้ามเดา
```

**Verifier ที่ใช้:** rule-based (นับ citation ต่อ claim) + ตรวจความขัดแย้งข้ามแหล่ง
**ข้อควรระวัง:** ห้ามใช้โมเดลตัวเดียวกันที่เขียนสรุป มาเป็นคนตัดสินว่าสรุปถูก (ดู A5.6)

---

### A5.3.3 ลูปจริงแบบที่ 3 — Content Loop

ใช้เมื่อ: เขียนคำโฆษณาสินค้า OTOP, โพสต์ขาย, คำอธิบายสินค้าส่งออก

```
DISCOVER  │ เก็บ: ข้อมูลสินค้าจริง + กลุ่มเป้าหมาย + brand voice + ข้อห้ามทางกฎหมาย
          │ (เช่น ห้ามอ้างสรรพคุณทางยาตาม พ.ร.บ. อาหาร)
          ▼
PLAN      │ กำหนดโครง: headline / จุดขาย 3 ข้อ / CTA
          │ เกณฑ์ผ่าน: ≤N คำ + มีคีย์เวิร์ดครบ + ผ่าน checklist คำต้องห้าม + โทนตรง brand
          ▼
EXECUTE   │ สร้าง 3 ทางเลือกที่ต่างกันจริง ไม่ใช่คำเดียวกันสลับที่
          ▼
VERIFY    │ ชั้น 1 (เครื่อง): นับคำ + regex คำต้องห้าม + เช็คคีย์เวิร์ด
          │ ชั้น 2 (คน/โมเดลอื่น): โทนใช่ไหม อ่านแล้วอยากซื้อไหม
          ▼
ITERATE   │ แก้เฉพาะข้อที่ตก แล้ววนใหม่ (สูงสุด 3 รอบ) → ส่งให้คนเลือกตัวสุดท้าย
```

**Verifier ที่ใช้:** ผสม — rule-based สำหรับสิ่งที่นับได้ + human-in-the-loop สำหรับรสนิยม

### A5.3.4 เทียบสามลูป

|---|---|---|---|
| **Verifier หลัก** | ตัวรันเทสต์ (แม่นสุด) | นับ citation + ตรวจขัดแย้ง | rule-based + คนตัดสิน |

## A5.4 Open Loop vs Closed Loop และ Single-agent vs Fleet

### A5.4.1 Open Loop vs Closed Loop

```
   OPEN LOOP (ยิงแล้วจบ)              CLOSED LOOP (มีวงย้อนกลับ)

   [Input] → [Model] → [Output]       [Input] → [Model] → [Output]
                                                    ▲         │
        ไม่มีการตรวจ                                 │         ▼
        ไม่รู้ว่าผิดหรือถูก                            └── [Verify] ──┘
                                             ถ้าไม่ผ่าน → ทำใหม่
```

| มิติ | Open Loop | Closed Loop |
|---|---|---|
| **นิยาม** | ทำครั้งเดียว ส่งผลออก ไม่ตรวจ | ตรวจผลแล้วป้อนกลับ วนจนผ่านเกณฑ์ |
| **ต้นทุนโทเคน** | 1× (ฐาน) | หลายเท่าของฐาน ตามจำนวนรอบ — **ต้องวัดด้วยการนับโทเคนจริงต่อภารกิจ** |
| **เวลาตอบสนอง** | เร็วที่สุด | ช้ากว่าตามจำนวนรอบ |
| **ความน่าเชื่อถือ** | ขึ้นกับดวงและคุณภาพ prompt | สูงกว่า แต่ **ดีแค่ไหนขึ้นกับคุณภาพ verifier** |
| **เหมาะกับ** | สรุปข้อความ, แปล, จัดรูปแบบ, ตอบคำถามทั่วไป, chat หน้าร้าน | โค้ด, งานกฎหมาย/การเงิน/การแพทย์, เอกสารส่งลูกค้า, งานที่ผิดแล้วเสียหาย |
| **ความเสี่ยงหลัก** | ส่งของเสียโดยไม่รู้ตัว | วนไม่จบ / verifier ห่วยทำให้มั่นใจผิด ๆ |

**กฎเลือก:** ถ้า *ต้นทุนของการตอบผิด* > *ต้นทุนของการวนซ้ำ* → ใช้ Closed Loop
งานความเสี่ยงสูงตามกฎเหล็กของกิลด์ AI/ML (กฎหมาย/การแพทย์/การเงิน) **บังคับ Closed Loop เสมอ**

---

### A5.4.2 Single-agent vs Fleet (กองเรือเอเจนต์)

```
   SINGLE-AGENT                        FLEET (Orchestrator + Sub-agents)

   ┌──────────────┐                    ┌──────────────────┐
   │  1 เอเจนต์    │                    │   ORCHESTRATOR   │
   │  1 context   │                    │  (แตกงาน+รวมผล)   │
   │  ทำทุกอย่าง   │                    └───┬────┬────┬────┘
   └──────────────┘                        │    │    │
                                      ┌────▼┐ ┌─▼──┐ ┌▼───┐
   • context เดียวจำทุกอย่าง            │ A  │ │ B  │ │ C  │  แต่ละตัว
   • ง่ายต่อการดีบัก                    └──┬─┘ └─┬──┘ └─┬──┘  context ของตัวเอง
   • ชนเพดาน context เมื่องานใหญ่          │     │     │
                                          └─────┴─────┘
                                        ส่งกลับแค่ "สรุป" ไม่ใช่ของดิบทั้งหมด
```

| มิติ | Single-agent | Fleet |
|---|---|---|
| **เหมาะกับ** | งานที่มีเส้นทางเดียว ขั้นตอนต่อเนื่อง | งานที่แตกเป็นสาขาอิสระได้ (ค้น 7 หัวข้อพร้อมกัน) |
| **ข้อดี** | เห็นภาพรวมครบ ดีบักง่าย ต้นทุนต่ำ | ขนานกันได้ แต่ละตัวมี context สะอาด ไม่ปนกัน |
| **ข้อเสีย** | context บวมเมื่องานยาว | ต้นทุนคูณตามจำนวนเอเจนต์ + ปัญหาการรวมผลที่ขัดแย้งกัน |
| **ต้นทุน** | ฐาน | สูงกว่าฐานหลายเท่า — **ต้องวัดด้วยการนับโทเคนรวมทุก sub-agent** |
| **จุดพังบ่อย** | ลืมข้อมูลต้นทางเมื่อถึงท้ายงาน | sub-agent ทำงานซ้ำกัน / ผลขัดแย้งแล้วไม่มีใครตัดสิน |

**กฎเลือก Fleet:** ใช้เมื่อครบ 3 เงื่อนไข
1. งานย่อย **เป็นอิสระต่อกันจริง** (ไม่ต้องรอผลของกันและกัน)
2. งานย่อยแต่ละชิ้น **กินบริบทเยอะ** จนถ้ารวมไว้ตัวเดียวจะล้น
3. มี **เกณฑ์รวมผล** ที่ชัดว่าถ้าผลขัดแย้งกันจะตัดสินอย่างไร

ถ้าขาดข้อใดข้อหนึ่ง → ใช้ single-agent ประหยัดกว่าและเสถียรกว่า

---

### A5.4.3 เมทริกซ์ตัดสินใจรวม

| ลักษณะงาน | Loop | จำนวนเอเจนต์ | เหตุผล |
|---|---|---|---|
| แปลข้อความสั้น / จัดรูปแบบ | Open | Single | ผิดแล้วแก้ง่าย ต้นทุนต่ำสุด |
| ตอบคำถามลูกค้าหน้าร้าน (FAQ) | Open + RAG | Single | ต้องเร็ว แต่ต้องยึดเอกสารจริง |
| สรุปสัญญา B2B / ตรวจข้อกฎหมาย | **Closed** | Single | ผิดแล้วเสียหาย ต้อง verify ทุกข้ออ้าง |
| เขียนโค้ด / migrate ระบบ | **Closed** | Single หรือ Fleet | เทสต์เป็น verifier ที่แม่น |
| วิจัยตลาดส่งออกหลายประเทศ | **Closed** | **Fleet** | แต่ละประเทศเป็นสาขาอิสระ กินบริบทเยอะ |
| ทำ Product Listing 500 SKU | Open (ต่อชิ้น) + Closed (ชุด) | Fleet | ขนานได้ แต่ต้องมี QC รวมท้าย |
| วินิจฉัย/ให้คำแนะนำสายการแพทย์ | **Closed + Human-in-loop** | Single | บังคับตามกฎเหล็ก ห้ามอัตโนมัติล้วน |

## A5.5 การประยุกต์กับ OpenThaiAi — ลูปไหนเหมาะกับกลุ่มไหน

อ้างอิง 6 กลุ่มผู้ใช้ตาม `CLAUDE.md` ข้อ 2

| กลุ่มผู้ใช้ | งานตัวอย่าง | ลูปที่แนะนำ | Verifier |
|---|---|---|---|
| 1. ผู้ผลิต | ตรวจฉลากสินค้าให้ตรงข้อกำหนด อย. | Closed / Single | rule-based checklist + RAG อ้างประกาศ |
| 2. คนกลาง | ตรวจเอกสารศุลกากร ตรวจพิกัดอัตราศุลกากร | Closed / Single | schema เอกสาร + ค้นพิกัดจากฐานจริง |
| 3. แพลตฟอร์ม | สร้าง Product Listing จำนวนมาก | Open ต่อชิ้น + Closed ตอน QC / Fleet | นับคำ + คำต้องห้าม + คีย์เวิร์ด |
| 4. ผู้บริโภค | ย่อยสิทธิสวัสดิการเป็นภาษาพูด | Open + RAG / Single | groundedness — ทุกสิทธิต้องชี้กลับเอกสารรัฐ |
| 5. ชุมชน/นักพัฒนา | ตรวจโค้ด, ตรวจร่างนโยบาย AI | Closed / Single หรือ Fleet | ตัวรันเทสต์ / checklist ธรรมาภิบาล |
| 6. สายวิชาชีพ | ค้นคำพิพากษา, ตรวจงบการเงิน | **Closed + Human-in-loop** / Single | ≥2 แหล่งอ้างอิง + คนวิชาชีพเซ็นรับรอง |

---

### ตัวอย่างที่ 1 — กลุ่มที่ 1 (ผู้ผลิต): ตรวจฉลากอาหารก่อนยื่น อย.

**ปัญหาจริง:** ผู้ประกอบการ OTOP เขียนฉลากเอง มักใส่ข้อความอ้างสรรพคุณเกินจริง ทำให้ถูกตีกลับ เสียเวลาหลายสัปดาห์

**ทำไมต้อง Closed Loop:** ผิดแล้วเสียหายจริง (ถูกปรับ/ตีกลับ) และมีเกณฑ์ตัดสินที่เขียนเป็นกฎได้

```
DISCOVER │ ดึงประกาศกระทรวงสาธารณสุขที่เกี่ยวกับประเภทอาหารนั้น (RAG)
PLAN     │ เกณฑ์ผ่าน: ครบ 9 รายการบังคับ + ไม่มีคำต้องห้าม + วันหมดอายุถูกรูปแบบ
EXECUTE  │ วิเคราะห์ฉลาก → ออกรายงานจุดที่ต้องแก้พร้อมมาตราอ้างอิง
VERIFY   │ ชั้น 1 rule: ตรวจรายการบังคับ + regex คำต้องห้าม
         │ ชั้น 2 grounding: ทุกข้อกล่าวหาต้องมีเลขประกาศกำกับ
ITERATE  │ ข้อไหนไม่มีเลขประกาศ → ค้นซ้ำ ถ้าไม่พบ → ตัดข้อนั้นออก + แจ้งว่า "ไม่พบข้อกำหนดยืนยัน"
```

---

### ตัวอย่างที่ 2 — กลุ่มที่ 4 (ผู้บริโภค): ย่อยสิทธิสวัสดิการรัฐ

**ปัญหาจริง:** ประชาชนไม่รู้ว่าตัวเองมีสิทธิอะไร เอกสารราชการอ่านยาก

**ทำไมใช้ Open Loop + RAG:** ต้องตอบเร็วในระดับแชท ผู้ใช้ทั่วไปทนรอ 30 วินาทีไม่ได้ แต่ **ห้ามตอบมั่ว** จึงบังคับให้ทุกคำตอบยึดเอกสารจริงและแสดงที่มา

```
DISCOVER │ ดึงประกาศ/ระเบียบสิทธิที่ตรงกับโปรไฟล์ผู้ใช้ (อายุ รายได้ พื้นที่)
PLAN     │ เกณฑ์ผ่าน: ทุกสิทธิที่กล่าวถึงต้องมีชื่อเอกสาร + วันที่ประกาศ
EXECUTE  │ ตอบเป็นภาษาพูด + ตารางสรุปสิทธิ + ขั้นตอนยื่น
VERIFY   │ ชั้นเดียว (เร็ว): เช็คว่ามี citation ครบทุกย่อหน้าที่อ้างสิทธิ
         │ ถ้าไม่พบเอกสาร → ตอบ "ไม่พบข้อมูลยืนยัน กรุณาติดต่อ <หน่วยงาน>"
```

> **หมายเหตุความปลอดภัย:** ห้ามเก็บข้อมูลส่วนบุคคล (เลขบัตร ปชช. รายได้) ลง log ตาม PDPA — ใช้เฉพาะในหน่วยความจำชั่วคราวของรอบนั้น

---

### ตัวอย่างที่ 3 — กลุ่มที่ 6 (สายวิชาชีพ): ผู้ช่วยค้นคำพิพากษาสำหรับทนายความ

**ปัญหาจริง:** ทนายต้องค้นฎีกาที่เกี่ยวข้อง การอ้างฎีกาที่ไม่มีอยู่จริงคือความเสียหายร้ายแรงต่อวิชาชีพ

**ทำไมต้อง Closed Loop + Human-in-loop:** ความเสี่ยงสูงสุด ระบบห้ามตัดสินใจแทนวิชาชีพ

```
DISCOVER │ แตกประเด็นข้อกฎหมาย → ค้นฐานคำพิพากษา (fan-out หลายคำค้น)
PLAN     │ เกณฑ์ผ่าน: ทุกฎีกาที่อ้าง ต้องตรวจสอบว่ามีเลขคดีจริงในฐาน
         │ + ต้องมี ≥2 แหล่งสำหรับข้อสรุปเชิงหลักกฎหมาย
EXECUTE  │ สรุปประเด็น + แนบข้อความจากคำพิพากษาจริง (ยกมาตรง ไม่เรียบเรียงใหม่)
VERIFY   │ ชั้น 1: ตรวจเลขคดีกลับไปที่ฐานข้อมูล — ไม่พบ = ตัดทิ้งทันที
         │ ชั้น 2: ตรวจว่าข้อความที่ยกมาตรงกับต้นฉบับ (exact match)
ITERATE  │ วนสูงสุด 3 รอบ → ส่งให้ทนายตรวจก่อนใช้เสมอ (บังคับ)
```

**ข้อจำกัดที่ต้องประกาศให้ผู้ใช้ทราบ:** ระบบนี้เป็น *เครื่องมือช่วยค้น* ไม่ใช่ *ความเห็นทางกฎหมาย*

### A5.5.4 โครงโค้ด Python — ลูป Verify-Retry แบบใช้ซ้ำได้

โค้ดนี้เป็น **โครง (skeleton)** ที่ทั้ง 3 ตัวอย่างข้างบนใช้ร่วมกันได้ เปลี่ยนแค่ `verifier` กับ `gather`

```python
"""
OpenThaiAi — Harness Loop Skeleton
โครงลูป Gather → Act → Verify → Retry ที่ใช้ซ้ำได้กับทุกกลุ่มผู้ใช้

หมายเหตุ: ยังไม่ได้วัดผลจริง — ต้องวัดด้วย Thai Eval Suite
(task completion rate, จำนวนรอบเฉลี่ย, โทเคนต่อภารกิจ) ก่อนอ้างตัวเลขใด ๆ
"""
from dataclasses import dataclass, field
from typing import Callable, Protocol, Any


# ── 1. สัญญาของ Verifier ─────────────────────────────────────────
@dataclass
class VerdictSchema:
    passed: bool
    failures: list[str] = field(default_factory=list)   # จุดที่ตก ระบุให้ชี้ได้
    evidence: dict[str, Any] = field(default_factory=dict)  # หลักฐานสำหรับ audit


class Verifier(Protocol):
    """ตัวตรวจต้องตัดสินได้ว่าผ่าน/ไม่ผ่าน ไม่ใช่ให้คะแนนความรู้สึก"""
    def check(self, draft: str, ctx: dict) -> VerdictSchema: ...


# ── 2. ตัวอย่าง Verifier แบบ rule-based (ตัดสินได้ด้วยเครื่อง) ────
class LabelComplianceVerifier:
    """ตัวอย่างกลุ่มที่ 1 (ผู้ผลิต) — ตรวจฉลากอาหาร"""

    REQUIRED_FIELDS = [
        "ชื่ออาหาร", "เลขสารบบอาหาร", "ส่วนประกอบ", "น้ำหนักสุทธิ",
        "วันเดือนปีที่ผลิต", "วันเดือนปีที่หมดอายุ",
        "ชื่อและที่ตั้งผู้ผลิต", "ข้อมูลสำหรับผู้แพ้อาหาร", "คำเตือน",
    ]
    FORBIDDEN_CLAIMS = ["รักษาโรค", "หายขาด", "ลดความอ้วน", "ต้านมะเร็ง"]

    def check(self, draft: str, ctx: dict) -> VerdictSchema:
        failures = []
        for f in self.REQUIRED_FIELDS:
            if f not in draft:
                failures.append(f"ขาดรายการบังคับ: {f}")
        for c in self.FORBIDDEN_CLAIMS:
            if c in draft:
                failures.append(f"พบข้อความต้องห้าม: '{c}'")
        # ทุกข้อกล่าวหาต้องอ้างเลขประกาศ
        if "ประกาศกระทรวงสาธารณสุข" not in draft:
            failures.append("ไม่มีการอ้างเลขประกาศกำกับ")
        return VerdictSchema(passed=not failures, failures=failures)


class GroundednessVerifier:
    """ตัวอย่างกลุ่มที่ 6 (วิชาชีพ) — ทุกเลขคดีที่อ้าง ต้องมีจริงในฐานข้อมูล"""

    def __init__(self, case_db_lookup: Callable[[str], bool]):
        self.lookup = case_db_lookup

    def check(self, draft: str, ctx: dict) -> VerdictSchema:
        import re
        cited = re.findall(r"ฎีกาที่\s*([\d/]+)", draft)
        failures = [f"อ้างฎีกาที่ไม่พบในฐานข้อมูล: {c}"
                    for c in cited if not self.lookup(c)]
        if not cited:
            failures.append("ไม่มีการอ้างคำพิพากษาใดเลย")
        return VerdictSchema(
            passed=not failures,
            failures=failures,
            evidence={"cited_cases": cited},
        )


# ── 3. ลูปหลัก ───────────────────────────────────────────────────
@dataclass
class LoopResult:
    output: str
    passed: bool
    rounds_used: int
    trace: list[dict] = field(default_factory=list)   # audit trail
    escalated: bool = False                           # ต้องส่งต่อมนุษย์ไหม


def harness_loop(
    task: str,
    gather: Callable[[str, list[str]], dict],   # DISCOVER — คืน context
    act: Callable[[str, dict, list[str]], str], # EXECUTE  — คืน draft
    verifier: Verifier,
    max_rounds: int = 3,                        # ⚠️ เพดานรอบ ห้ามละเว้น
    token_budget: int | None = None,
) -> LoopResult:
    """
    Gather → Act → Verify → Retry
    ทุกลูปต้องมีเงื่อนไขหยุด 2 ชั้น: จำนวนรอบ และงบโทเคน
    """
    failures: list[str] = []
    trace: list[dict] = []
    draft = ""
    spent = 0

    for rnd in range(1, max_rounds + 1):
        # ── GATHER: รอบถัดไปส่ง failures กลับไปด้วย เพื่อค้นให้ตรงจุดที่ตก
        ctx = gather(task, failures)

        # ── ACT
        draft = act(task, ctx, failures)
        spent += ctx.get("tokens_used", 0)

        # ── VERIFY (ต้องเป็นคนละตัวกับผู้สร้าง ดู A5.6 กับดักที่ 2)
        verdict = verifier.check(draft, ctx)
        trace.append({
            "round": rnd,
            "passed": verdict.passed,
            "failures": verdict.failures,
            "evidence": verdict.evidence,
        })

        if verdict.passed:
            return LoopResult(draft, True, rnd, trace)

        # ── ITERATE: ถ้ารอบนี้ตกเรื่องเดิมเป๊ะ ๆ แปลว่าวินิจฉัยผิดระดับ หยุดเลย
        if verdict.failures == failures:
            return LoopResult(draft, False, rnd, trace, escalated=True)
        failures = verdict.failures

        if token_budget and spent >= token_budget:
            break

    # ครบเพดานแล้วยังไม่ผ่าน → ส่งต่อมนุษย์ ห้ามส่งของที่ยังไม่ผ่านให้ผู้ใช้เงียบ ๆ
    return LoopResult(draft, False, max_rounds, trace, escalated=True)
```

**สิ่งที่ยังไม่ได้ทำในโค้ดนี้ (ต้องทำก่อนใช้จริง):**
- ยังไม่ผูกกับโมเดลจริง — `gather` / `act` เป็น callable ที่ต้อง implement ต่อ
- ยังไม่มี Guardrails ชั้น input (prompt injection) และ output (PII/hate speech)
- ยังไม่มีการวัดผล — **ต้องวัดด้วย Thai Eval Suite** ก่อนอ้างว่าดีขึ้น

## A5.6 กับดักที่พบบ่อย

| # | กับดัก | เกิดอะไรขึ้น | ทางแก้ |
|---|---|---|---|
| 1 | **ยัด context จนล้น** | โยนเอกสาร 200 หน้าเข้าไปหวังให้ฉลาดขึ้น แต่คำตอบกลับแย่ลง — โมเดลหาของสำคัญไม่เจอในกองข้อมูล | re-rank แล้วเอาเฉพาะ top-k ที่เกี่ยวจริง วัดด้วย recall@k เทียบก่อน/หลัง |
| 2 | **verify ด้วยโมเดลตัวเดียวกับที่สร้าง** | โมเดลที่แต่งเรื่องขึ้นมา ก็จะเชื่อเรื่องที่ตัวเองแต่ง — ตรวจแล้วผ่านหมด แต่ผิดหมด | ใช้ตัวตรวจที่เป็นอิสระ: เครื่อง (test/schema/regex) > โมเดลคนละตัว/คนละ context > คน |
| 3 | **ลูปที่ไม่มีเงื่อนไขหยุด** | วนแก้ไปเรื่อย ๆ เผาโทเคนจนงบหมด หรือแก้จุด A ทำให้จุด B พัง แล้ววนกลับมาแก้ A | บังคับเพดาน 2 ชั้น: `max_rounds` + `token_budget` และตรวจว่า "ตกเรื่องเดิมซ้ำ" ให้หยุดทันที |
| 4 | **เกณฑ์ผ่านที่ตัดสินไม่ได้** | เขียนว่า "คำตอบต้องดี" — ไม่มีใครรู้ว่าดีคืออะไร ลูปจึงไม่มีความหมาย | เกณฑ์ต้องเป็นสิ่งที่เครื่องหรือคนตัดสินได้ตรงกัน: "มี citation ทุกย่อหน้า", "เทสต์เขียว", "≤120 คำ" |
| 5 | **แก้ผิดระดับ** | ตอบผิดข้อเท็จจริงแล้วไปแต่ง prompt — เสียเวลาเป็นสัปดาห์โดยอาการไม่ดีขึ้น | ใช้ตาราง A5.2 วินิจฉัยก่อนลงมือทุกครั้ง |
| 6 | **สร้าง Harness ให้งานที่ prompt เดียวก็จบ** | over-engineer — ระบบซับซ้อน ช้า แพง ดีบักยาก โดยไม่ได้อะไรเพิ่ม | เริ่มจาก Prompt เสมอ ขยับขึ้นระดับเมื่อวัดแล้วว่ายังไม่พอ |
| 7 | **Fleet ที่ sub-agent ทำงานซ้ำกัน** | แตก 5 เอเจนต์ ค้นเรื่องเดียวกัน 5 รอบ จ่าย 5 เท่าได้ผลเท่าเดิม | แบ่งขอบเขตให้ชัดก่อนแตก + ให้ orchestrator ตรวจการทับซ้อน |
| 8 | **สรุปทับข้อมูลสำคัญตอน compact** | ยุบบทสนทนาเก่าแล้วเผลอทิ้งข้อจำกัดที่ผู้ใช้บอกไว้ตอนต้น | แยก "ข้อเท็จจริงถาวร" (ข้อจำกัด, ความต้องการ) ออกไปเก็บใน memory ห้ามยุบทิ้ง |
| 9 | **ไม่มี audit trail** | ระบบตอบผิด แต่ไล่ย้อนไม่ได้ว่าผิดที่ขั้นไหน | บันทึก trace ทุกรอบ: context ที่ใช้, draft, verdict, failures |
| 10 | **อ้างว่าดีขึ้นโดยไม่ได้วัด** | เปลี่ยนแล้วรู้สึกว่าดีขึ้น เขียนลงเอกสารว่า "แม่นขึ้นมาก" — พอเจอเคสจริงพัง | ทุกการเปลี่ยนแปลงต้องมี baseline + ตัวเลขหลังแก้ ถ้ายังไม่ได้วัด ให้เขียนว่า "ยังไม่ได้วัด" |
| 11 | **Guardrails ชั้นเดียว** | กรอง output อย่างเดียว แต่ input โดน prompt injection สั่งให้ข้ามกฎไปแล้ว | ต้องมีทั้ง input guardrail (injection) และ output guardrail (PII, hate speech) |
| 12 | **ลืมว่าไทยไม่มีเว้นวรรค** | ใช้ chunker ภาษาอังกฤษตัดเอกสารไทย ได้ก้อนที่ตัดกลางคำ ความหมายเพี้ยน retrieval พัง | ใช้ตัวตัดที่เข้าใจภาษาไทย + ตรวจก้อนตัวอย่างด้วยตาก่อน index ทั้งคลัง |
